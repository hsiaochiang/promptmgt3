## AI

可以，而且我建議用「人（角色）＋流程（Gate）＋自動化（視覺回歸）」三件事一起做，才會穩定地把前端風格維持在你期待的 style。

---

## 一、可行作法總覽（你問的「另一個 agent / skill / 其他方式」）

### 作法 A｜建立第二個「UI/UX Reviewer GPT」（最接近你想要的「另一個角色」）
你保留原本的 Coding Agent（負責寫程式），另外建立一個專門做「版面與視覺風格審查」的 GPT。

- OpenAI 允許你建立自訂 GPT（可放入指令、知識檔等），作為固定角色使用。 citeturn0search4turn0search0  
- 你也可以把這個 Reviewer GPT 放進同一個 Project 工作區，讓它在同一套專案脈絡下運作（例如固定的設計規範檔）。 citeturn0search1

**適用情境**：你已經有「你想要的 Notion 風格」或既定 UI 原則，希望每次改動都有人把關。

---

### 作法 B｜不建第二個 GPT，改用「同一個 Agent 的雙模式審查流程」（最快上手）
你仍用同一個對話／同一個 Agent，但要求它在每次提交前一定要切換成「Reviewer 模式」做一輪檢查（等同內建 Code Review / Design Review gate）。

**優點**：不用切工具、不用管理多個 GPT。  
**缺點**：容易被寫程式的脈絡帶走，審查會不夠「獨立」。

---

### 作法 C｜用「視覺回歸測試」把 style 變成可驗證的規格（最可靠）
如果你真的在意「是否符合期待的 style」，純文字審查不夠，必須上自動化比對：

- Playwright 支援截圖基準（baseline）與後續比對，可用 `toHaveScreenshot()` 做視覺差異檢測。 citeturn0search2  
- 若你有元件化（React/Next 常見），Storybook 的 visual tests 與 Chromatic 這類服務可以對「元件級」做快照比對，更能穩定抓到跑版或風格漂移。 citeturn0search7turn0search3

**適用情境**：你希望「改了就知道有沒有變醜／變不一致」，而不是靠感覺。

---

## 二、我建議你的最佳組合（實務上最有效）
**A（UI Reviewer GPT）＋ C（視覺回歸）**  
原因：Reviewer 只靠文字很難精準；但如果有「截圖 diff」或「元件快照差異」，Reviewer 的判斷就會非常準，且可形成交付門檻（Gate）。

---

## 三、落地做法（你可以直接照這個流程建立）

### 1) 先做一份「Style Contract」（沒有這個，Reviewer 無法客觀判定）
用一個 `UI-STYLE.md`（或你專案既有的文件格式）寫清楚：
- 版面：欄寬、grid、容器最大寬度、留白規則（8px scale 等）
- 字體：字級階層、行高、字重
- 色彩：主色、灰階、狀態色、禁用色
- 元件：Button/Input/Table/Card 的樣式規範與禁用寫法
- Notion-like 你想抄的「關鍵特徵」：例如克制的陰影、弱化邊框、強留白、資訊密度、hover 行為等

這份文件之後會成為 Reviewer 的「判卷標準」。

---

### 2) 建立「UI/UX Reviewer GPT」（作法 A）
依 OpenAI 的自訂 GPT 建立方式建立一個新 GPT（Configure / Instructions / Knowledge）。 citeturn0search0  
再把 `UI-STYLE.md`、design tokens、常用元件規範（如果有）放進 Knowledge（或 Project 檔案）讓它能長期沿用。 citeturn0search12turn0search1

**Reviewer GPT 的指令模板（可直接貼到 Instructions）**：
```text
你是「前端 UI/UX Reviewer」，只負責審查視覺與互動一致性，不寫程式碼。

輸入會包含：
1) 變更目的（user story）
2) 變更前/後截圖（或 Storybook 連結、或 Playwright screenshot diff 描述）
3) 相關元件/頁面檔案路徑（可選）

你的輸出必須包含：
A. 結論：Pass / Conditional Pass / Fail
B. 與 UI-STYLE.md 的符合度檢查（逐條引用規則）
C. 具體修改建議（以可操作的 checklist 表達）
D. 風險：可能造成不一致的範圍（哪些頁/元件會被波及）
限制：
- 若缺少截圖或可視證據，一律回覆「Evidence insufficient」並列出需要的證據清單。
```

---

### 3) 把「視覺回歸」接進你的開發節奏（作法 C）
你可以用 Playwright 先做「頁面級」快照，至少把主要頁面先鎖住：

- Playwright 內建有視覺快照比對能力（baseline vs 現況）。 citeturn0search2  
- 元件更細的話，用 Storybook 的 visual tests / Chromatic 走「元件級」更穩。 citeturn0search7turn0search3

**你實際的工作節奏可以長這樣：**
1. Coding Agent 完成一段 UI 調整 → 產出「變更前/後截圖」或「diff」
2. 丟給 Reviewer GPT → 出具 Pass/Fail 與 checklist
3. Fail 就回到 Coding Agent 改
4. Pass 才合併／提交

---

## 四、你現在就能先用的「最小可行版本」（不用等整套工具上線）
如果你今天就要開始跑，我建議你先做到兩件事就好：
1) 立刻建立 `UI-STYLE.md`（先寫 10 條最重要的風格規則即可）  
2) 每次 UI 調整，都固定產出：
   - 1 張「變更前」截圖  
   - 1 張「變更後」截圖  
   - 1 段變更目的（為什麼改）

然後丟給 Reviewer（不管是第二個 GPT 或同一個對話切 Reviewer 模式），你的「風格是否如預期」就會開始可控。

## AI

可以，但要先釐清一個現實：**Coding agent（Copilot / Codex）本質上主要讀程式碼與檔案**，它不一定「看得到」你瀏覽器中實際渲染後的畫面。因此，要讓它能判斷「是否符合你期待的 style」，通常要用「兩段式」設計：

1) **把你要的 style 變成可被引用的規範（文字化、可檢核）**  
2) **把實際 UI 變成可檢核的證據（例如 screenshot baseline / Storybook snapshots）**  
然後再讓 agent 扮演「Design Reviewer / UI Guardian」去比對規範與證據。

下面給你三種做法（由輕到重），每一種都能落地。

---

## 做法 A（最務實、成本最低）：用「Copilot 指令檔」建立固定的 Design Reviewer 角色

### A1. 建立你專案的 UI Style Guide（文字規範）
在 repo 放一份例如：`/docs/ui-style-guide.md`，內容至少包含：
- 視覺目標：Notion-like / B2B 金融風 / 極簡等
- Layout：grid、留白、最大寬度、sticky header 等
- Typography：字級階層、字重、行高
- 元件規範：按鈕、表格、tag、modal 的樣式與行為
- 禁止事項：例如「避免陰影過重」「避免漸層」「避免大圓角」等

### A2. 用 `.github/copilot-instructions.md` 固化「審美檢核角色」
VS Code 支援用 `.github/copilot-instructions.md` 讓 Copilot Chat 自動套用指令（需開啟設定 `github.copilot.chat.codeGeneration.useInstructionFiles`）。citeturn0search6turn1search4  
GitHub 也支援 repo custom instructions，並可用於 Copilot code review / coding agent。citeturn0search10turn1search0turn1search1

你可以把「Design Reviewer」規則直接寫進去，例如（示意）：

```md
# .github/copilot-instructions.md（節錄：UI Style Reviewer）

你同時扮演「UI Style Reviewer」：
- 任何前端 UI 改動（components/pages/styles/tailwind classes）都必須符合 /docs/ui-style-guide.md
- 請用 checklist 檢核：排版、留白、字級階層、元件一致性、互動狀態（hover/focus/disabled）、RWD、a11y
- 若無法從程式碼判斷視覺效果，請要求我提供：
  1) 對應頁面的截圖（或 Playwright baseline/diff 結果）
  2) Storybook story（若有）
- 回覆格式固定：
  1) 符合項目
  2) 不符合項目（逐點對照規範章節）
  3) 具體修改建議（以可直接貼回 code 的方式描述 class/元件調整）
```

### A3. 日常使用方式（你不用真的「開另一個 agent」）
你只要在 VS Code 裡把同一個 Copilot（或 Codex）用不同提示詞喚起不同模式即可：
- 「Builder」提示詞：請實作 xxx
- 「Design Reviewer」提示詞：請依照 ui-style-guide.md 審核我剛剛這次變更是否符合 Notion-like 風格，列出不符合點與修改建議

這種方式的優點是：**最省事**，缺點是：如果沒有截圖/可視化測試，agent 很容易只能從 class/元件結構做「推測」。

---

## 做法 B（更像你要的“另一個 agent”）：用 VS Code Copilot Agent Mode / OpenAI Codex 分工

### B1. Copilot Agent Mode（偏「多步任務的同事」）
VS Code 已提供 Copilot agent mode：能讀 repo、提案修改、跑 terminal / tests 等，適合把「審核 style」變成一個可重複任務流程。citeturn0search15turn0search11  
（若你未來要讓它自動去跑截圖測試、彙整差異，這種模式更順。）

### B2. OpenAI Codex IDE Extension（你可以把它當成另一個獨立工作同仁）
Codex VS Code extension 可在 IDE 內 side-by-side 使用，並支援不同 approval mode、可跑指令、也可 delegate 到 cloud。citeturn0search4turn1search2turn0search12  

實務上你可以分工：
- Copilot：負責快速修改 UI / refactor
- Codex：固定扮演「UI Style Reviewer」，每次你貼 PR diff 或指定檔案範圍，請它輸出 checklist 審核

> 關鍵：不論 Copilot 或 Codex，你都需要把「規範」放在 repo（A1/A2），否則 reviewer 的判斷標準會漂移。

---

## 做法 C（最可靠、最接近“客觀判定”）：導入視覺回歸測試，讓 agent 依結果判讀

如果你希望「像驗收一樣」判定是否符合 style，**視覺回歸測試（visual regression）**會是核心。

### C1. Playwright screenshot baseline/diff（頁面或元件）
Playwright Test 支援 `toHaveScreenshot()`：第一次產生 baseline，後續比對差異並產生 diff。citeturn0search0turn0search20  

你可以把流程定義成：
1) 你改完 UI  
2) 跑 Playwright screenshot tests  
3) 產生 baseline/actual/diff  
4) **Design Reviewer agent 讀測試結果與你對照 style guide，判斷差異是否可接受**

### C2. 若你有元件化：Storybook + Visual Tests（Chromatic）
Storybook 文件本身就把「Visual tests」定位為高效率的元件外觀驗證方式。citeturn2search1  
Chromatic 也提供以 baseline snapshots 做 commit-to-commit 視覺比對的工作流。citeturn2search0turn2search5turn2search9  

這套的好處是：你不只驗「頁面」，也能驗「元件狀態（hover/disabled/variants）」。
