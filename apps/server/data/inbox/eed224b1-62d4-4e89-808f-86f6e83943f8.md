## 1) 分支是什麼、為什麼要用

- **分支的本質：** 在 Git 裡，分支是一個「指向某個 commit 的可移動指標」。你在分支上提交（commit），分支指標就往前移動。citeturn0search0turn0search16  
- **分支的目的：** 用來**隔離變更**，避免直接污染主線（main/master），讓多人並行、回溯、審查、釋出都更可控。citeturn0search14turn0search1

---

## 2) 何時該「開分支」：判斷原則（最實用）

你可以用這三個判斷原則快速決定：

### 原則 A：只要「不是立刻要上線到主線」就開分支
- 例如：新功能、重構、實驗、需求不確定、需要 review/測試。

### 原則 B：只要「可能需要退回或暫停」就開分支
- 例如：做到一半被插單、要切換處理緊急 bug、或要 A/B 比較方案。

### 原則 C：只要「要讓別人看見你做了什麼」就開分支
- 你要開 PR（Pull Request）讓同仁 review、跑 CI、留下討論紀錄。GitHub 對分支＋PR 的流程建議就是這樣運作。citeturn0search11turn0search14

---

## 3) 常見適用情境（用「分支類型」來記最直覺）

### (1) Feature Branch：新功能/需求（最常用）
- **何時用：** 一個 user story、一張工單、一個需求
- **理由：** 把功能開發隔離在專用分支，不影響 main，CI 也更穩定 citeturn0search1turn0search10
- **命名建議：** `feature/<ticket>-<short-desc>`  
  例：`feature/FI-123-prompt-tagging`

### (2) Bugfix Branch：非緊急 bug 修正（一般修 bug）
- **何時用：** 測試環境或開發階段的缺陷修補
- **命名建議：** `bugfix/<ticket>-<short-desc>`

### (3) Hotfix Branch：正式環境緊急修補（需要快速上線）
- **何時用：** production 掛了、法遵/資安必須立刻修、重大營運風險
- **理由：** 要從「目前線上版本」快速切出修補，修完立刻併回主線（並同步回開發線）——Pro Git 的範例流程就是這樣描述。citeturn0search3turn0search16
- **命名建議：** `hotfix/<ticket>-<short-desc>`

### (4) Release Branch：版本釋出準備（多團隊/版本控需要）
- **何時用：** 你們需要「凍結功能」只做修 bug、調設定、補文件，等待一個版本一起上線
- **典型在 Gitflow：** feature 從 develop 來、完成後回 develop，release 負責釋出準備。citeturn0search4
- **命名建議：** `release/2026.01` 或 `release/v1.4.0`

### (5) Spike/Experiment Branch：探索/試做（尤其適合你現在的雛形階段）
- **何時用：** 技術可行性、UI 原型、AI agent 嘗試、第三方套件評估
- **命名建議：** `spike/<topic>` 或 `exp/<topic>`
- **好處：** 允許你快速試錯，不會污染正式開發線；最後「要就 cherry-pick / 併入、不用就刪掉」。

## 4) 兩種主流工作流：你該選哪一種

### 方案 A：GitHub Flow（較輕量，適合快速迭代、SaaS、單一主線）
- **概念：** 從 default branch（main）切 feature → PR → review/CI → merge 回 main。citeturn0search11turn0search14
- **適用：** 小中型團隊、部署頻繁、想降低流程複雜度。

### 方案 B：Gitflow（較重，適合多版本並行、釋出節奏明確）
- **概念：** main（穩定）/develop（整合）/feature/release/hotfix 分工明確。citeturn0search4
- **適用：** 有多環境、多版本、釋出需要凍結窗口（例如銀行/大型企業專案常見）。

## 5) 實作範例（指令 + 你會看到什麼）

### 範例 1：做一個新功能（Feature Branch + PR）
情境：你要新增「提示詞自動貼標」功能，但不想影響 main。

1. 從 main 切分支
```bash
git switch main
git pull
git switch -c feature/FI-123-auto-tag
```

2. 開發並提交
```bash
git add .
git commit -m "feat: add auto-tagging draft"
```

3. 推到遠端，準備開 PR
```bash
git push -u origin feature/FI-123-auto-tag
```

你會看到的結果：
- 遠端出現同名分支
- GitHub 會提示你「Compare & pull request」
- PR review 通過後再 merge 回 main（符合 GitHub Flow 的典型做法）。citeturn0search11

---

### 範例 2：正式環境緊急修補（Hotfix）
情境：production 出現重大 bug，必須立刻修。

```bash
git switch main
git pull
git switch -c hotfix/FI-201-login-crash
# 修正後
git add .
git commit -m "fix: resolve login crash"
git push -u origin hotfix/FI-201-login-crash
```

接著：
- 開 PR → merge 回 main → 走部署
- 若你同時有 develop，也要把同樣修補同步回 develop（Gitflow 常見要求）。citeturn0search3turn0search4

---

### 範例 3：試做/探索（Spike），最後決定不要
情境：你在評估某套 UI table/board 元件或 AI agent 方案，不確定會不會採用。

```bash
git switch -c spike/ui-board-component
# 試作一些 commit...
git commit -am "spike: try board component"
```

如果最後不要：
```bash
git switch main
git branch -D spike/ui-board-component
```

分支刪除屬於標準 branch 操作（建立/刪除/管理皆是 Git 的基本能力）。citeturn0search15turn0search2

## 6) 最容易踩的誤區（你可以用來對內宣導）

1) **直接在 main 上做功能**：一旦出錯或做到一半，回收成本高、也難 review。  
2) **一個分支塞多個需求**：PR 太大、review 困難、回溯痛苦。建議「一需求一分支」。  
3) **分支不刪**：遠端分支越堆越多，後續維運與搜尋成本上升。GitHub 也提供分支刪除與管理的指引。citeturn0search19turn0search14  

---

## 7) 你現在（雛形 + Coding Agent）最建議的分支策略

以你目前「先把雛形/UI/動線做到像產品級，再交給 Coding Agent 大量產出」的節奏，我會建議：

- **main：** 永遠可跑、可展示的穩定版本（Demo 可用）
- **feature/**：每個功能一支（讓 agent 改動可控、PR 可檢視差異）
- **spike/**：所有探索性嘗試都丟這裡（做完要就併入、不要就刪）

這樣你在 VS Code / GitHub 上 review agent 產出時，可以把「每次改動」都限制在單一分支、單一目的，回頭修正會非常有效率。
