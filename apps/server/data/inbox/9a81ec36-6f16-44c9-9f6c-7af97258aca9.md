## 1) 「漏洞密度（Vulnerability Density）」的定義是什麼？

在 Checkmarx 的指標語意中，「漏洞密度」本質上是把**漏洞數量**用**程式碼規模（LOC, Lines of Code）**做標準化，讓不同專案/不同版本的程式碼可以用同一尺度比較。

- Checkmarx One 的文件定義：**Vulnerability Density = 每千行程式碼（kLOC）中包含的漏洞數**。 citeturn1view0  

因此若以 kLOC 表示，公式可寫成：

\[
\text{Vulnerability Density (per kLOC)} = \frac{\text{漏洞數}}{\text{LOC}} \times 1000
\]

> 你報告上的「Density: 5/10000（漏洞/LOC）」或「0/100（漏洞/LOC）」屬於**報告模板呈現方式**：用固定基準（例如每 10,000 LOC 或每 100 LOC）去表達「每多少 LOC 有幾個漏洞」。不同版本/模板可能顯示的基準不一致（你兩份報告就剛好是 10,000 與 100）。外部案例也可見類似格式（例如 Density 0/100）。 citeturn1view2  

### 依你 Web 報告做一次「可比較」換算（用 kLOC）
- Web 報告：漏洞密度顯示 5/10000（且你描述確實有落差），若以「漏洞數=5、LOC=47,333」換算：
  - 每 kLOC 漏洞密度 = 5 / 47,333 × 1000 ≈ **0.106 / kLOC**
- API 報告：0（不論以何基準，換算後仍為 0）

## 2) 為什麼同一份程式，用同一工具，漏洞密度會差很多？

你這個案例最關鍵的差異不是 LOC，而是 **Preset（規則/查核集合）不同**：

- Web 報告用「OWASP TOP 10 - 2021（網站服務）」：偏向 Web App 常見風險（例如注入、XSS、存取控制、設定錯誤等）。
- API 報告用「OWASP TOP 10 API」：偏向 API 特有風險（例如 API 授權、物件層級授權、資源耗用、API 資料曝光等）。

**Preset 不同 → 啟用的 Queries / 規則集合不同 → 被判定為漏洞的“事件”也不同 → 漏洞數不同 → 密度不同。**  
所以你看到「Web 有 5、API 為 0」在方法學上是合理的：它不代表工具不一致，而是代表「你拿兩把不同的尺在量不同的風險集合」。

補充一點：在 Checkmarx One 的說明中，LOC/密度等指標會受「掃描/過濾」流程影響（例如 LOC 計算在過濾之後進行，避免超過 LOC 限制）。 citeturn3view0  
雖然你這兩份報告 LOC 相同（47,333），但這段仍提醒你：**只要你調整報告/結果的納入條件，密度就可能跟著變**（因此提交客戶時要把「Preset/過濾條件」寫清楚）。

## 3) 要提交哪一份報告給客戶比較好？

### 原則：以「合約/需求範圍」決定主報告，另一份作為附件或補充
我建議的交付方式（最不容易出事）：

1) **主報告：提交符合本次交付範圍的那份**
   - 若本次是「網站/前後台 Web 系統」掃描交付 → 主報告用 **OWASP Top 10 2021（Web）**
   - 若本次是「API 安全」掃描交付 → 主報告用 **OWASP Top 10 API（API）**
2) **副報告：另一份一起附上，並在摘要頁用 2–3 句話解釋**
   - 明確寫：「兩份報告使用不同 Preset（衡量不同風險集合），因此漏洞數/密度不可直接當作同一把尺比較。」

這樣做的好處是：客戶不會拿「API 報告 0 漏洞」去誤解成「整體 0 漏洞」，也不會把「Web 有 5」誤解成「API 也一定有 5」。

### 若你被迫只能二選一
在不確定客戶期待、且你想降低後續爭議的情況下，**我會選擇提交“較保守、涵蓋面較廣且確實有發現事項”的那份（也就是 Web / OWASP Top 10 2021）**，並在報告首頁摘要補一句：「另已以 OWASP Top 10 API 規則集檢視 API 類風險，結果為 0。」  
理由很務實：只交 0 的那份，客戶往往會把它解讀成「全系統無風險」，後續若被第三方掃到問題，容易回頭質疑你們交付不實。
