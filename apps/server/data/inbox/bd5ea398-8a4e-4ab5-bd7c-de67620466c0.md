# 前端設計參考規格

**Created**: 2025-12-26T07:43:35.221259

## User

需要跟你討論一下
關於前端網頁設計 就是按鈕 配色 排版 動線規劃 等等
需要請ChatGPT協助設計時 如果我提供一個網站做參考 有幫助嗎
如何訂定一個參考的範例 給ChatGPT或Coding Agent在產生前端相關元件的時候 有所依循

## AI

可以，而且通常很有幫助；但關鍵在於「你提供的不是一個網址」，而是一套可被遵循、可被驗收的「設計參考規格」。網址只是一個起點；真正讓 ChatGPT / Coding Agent 產生一致 UI 的，是你把參考網站的設計語言拆成可落地的規則與元件標準。

以下提供一套你可以直接拿去對內報告、也能給 AI 生成前端時依循的做法。

---

## 1) 提供參考網站有沒有幫助：有，但要避免兩個常見失敗模式

### 有幫助的原因
- **縮短「設計語言對齊」時間**：按鈕大小、圓角、陰影、字級階層、留白密度等，參考站能快速定錨。
- **統一交互模式**：例如列表頁的篩選/搜尋/排序放哪、卡片點擊區域、彈窗/抽屜的使用時機。
- **降低生成落差**：沒有參考時，AI 會用「通用審美」猜；有參考規格時，會比較穩定。

### 失敗模式 A：只丟網址
AI 無法穩定「抽象出規則」，容易每頁風格不一致，或抓到不重要的視覺元素。

### 失敗模式 B：參考站太複雜或是巨型設計系統
例如 Stripe、Notion、Linear 這類很成熟的產品，細節很多，若你沒下「取用範圍」，AI 會學到太多、反而產出冗長且難維護的 UI。

---

## 2) 怎麼訂定「參考範例」：用 3 層篩選法選 1–2 個就好

### 第 1 層：同領域 / 同使用情境
- 你做的是「提示詞管理 / 專案管理 / 內部工具」：就找 **B2B SaaS、後台管理、工具型產品**。
- 避免拿行銷型網站或電商前台當唯一參考（動線與元件會不一樣）。

### 第 2 層：同密度（資訊量相近）
- 你的頁面有表格、篩選器、側邊欄、詳情面板：就找同樣是 **表格 + 明細** 的介面。
- 不要找以視覺大圖為主的站。

### 第 3 層：同技術落地能力
- 你若要用 Tailwind + shadcn/ui：選參考站時要偏「簡潔、可用通用元件實作」。
- 太多客製動畫、特殊插畫、極端排版的參考站會讓 agent 很難落地。

建议：**主參考 1 個（風格與規則）+ 次參考 1 個（某些元件交互）**。不要超過 2 個。

---

## 3) 把「參考網站」變成 AI 可用的「參考規格」：建議你固定輸出這 6 個區塊

你可以要求自己每次提供參考，都至少補齊以下六項。這會大幅提升一致性。

### A. 設計目標（Design Intent）
- 例：B2B 工具、資訊密度中高、偏理性、可長時間使用、不炫技。
- 產出要以「清楚、可掃讀、可操作」為優先。

### B. 版面骨架（Layout Skeleton）
用清楚的結構描述，例如：
- Header：固定高度、左側 logo/專案名、右側全域搜尋/使用者選單  
- Left Sidebar：專案/分類導覽  
- Main：列表 + 篩選工具列  
- Right Panel：點擊列表後顯示詳細內容（或用 Drawer）

### C. 視覺 Token（Design Tokens）
不需要很長，但要「可被實作」：
- 字級階層：H1/H2/Body/Caption 的大小與字重
- 圓角：例如卡片 12px、按鈕 10px
- 間距：8pt spacing（8/16/24/32）
- 陰影：1–2 種層級
- 色彩：Primary / Secondary / Neutral / Danger / Success（可直接用 Tailwind 的色階範圍定義）

### D. 元件規格（Component Specs）
至少列你一定會用到的：
- Button：Primary / Secondary / Ghost / Destructive，並定義尺寸（sm/md/lg）
- Input：搜尋框、一般輸入、文字區塊
- Table：欄位對齊、hover、row click 行為
- Card：列表卡片的資訊呈現方式
- Modal/Drawer：用於新增/編輯/檢視的時機

### E. 動線與狀態（User Flow + States）
動線要能驗收，例如：
- 列表頁：搜尋 → 篩選 → 點一筆 → 右側詳情 → 編輯 → 儲存 → Toast 成功訊息
- 空狀態、Loading、Error、無權限

### F. 禁止項（Anti-patterns）
這很重要，避免 agent 發揮過頭：
- 不要做複雜動畫
- 不要用過多顏色（最多 1 個主色 + 中性色）
- 不要在同頁混用 table 與卡片展示同一份資料
- 不要用過深陰影或擬物

## 4) 你可以怎麼提供「參考範例」給 ChatGPT / Coding Agent：三種成熟做法

### 做法 1：最推薦（可控且穩）
**把參考站的關鍵畫面截圖 + 你自己的規格條列**  
- 截圖：列表頁、詳情頁、編輯彈窗、空狀態（4 張就夠）
- 再附上第 3 節那 6 區塊規格
優點：agent 產出一致性最高；也不會過度依賴「去看網址」。

### 做法 2：給 URL，但必須限制「取用範圍」
你可以這樣寫：
- 「只參考：字級階層、按鈕樣式、留白密度、列表 + 詳情雙欄布局」
- 「不要參考：插畫、動態效果、品牌色」
優點：少準備截圖；缺點：一致性仍略低於做法 1。

### 做法 3：自己先定義 Design System（最適合長期專案）
把 tokens + 元件規格寫成一份 `ui-guidelines.md`（或 `design-spec.md`），以後每次叫 agent 產 UI 都附上該檔內容。
優點：長期維護成本最低；最適合你這種會持續擴功能的內部工具。

## 5) 給 Coding Agent 的「可直接套用」參考規格範本（你可以複製改字）

你後續只要把參考網站與你的偏好填進去，就能穩定生成 UI。

- **Reference**  
  - Primary reference:（網址或產品名）  
  - Secondary reference:（可選）  
  - Use scope: typography / spacing / button style / layout pattern  
  - Exclude: branding illustrations / heavy animations / marketing visuals

- **Design intent**  
  - B2B admin tool, medium-high information density, minimalistic, clarity-first.

- **Layout skeleton**  
  - App shell: header + left sidebar + main content  
  - Main page pattern: toolbar (search/filter/actions) + table list + right detail panel (or drawer)

- **Tokens**  
  - Spacing: 8pt grid  
  - Radius: card 12, input/button 10  
  - Typography: H1/H2/body/caption sizes  
  - Colors: primary + neutral + semantic (success/warn/danger)  
  - Shadow: 2 levels only

- **Components**  
  - Buttons: primary/secondary/ghost/destructive + sm/md sizes  
  - Table: row hover + row click opens detail panel  
  - Form: label alignment, required mark, inline error  
  - Feedback: toast for success/error; empty state template

- **Flow & states**  
  - Create/Edit via modal or drawer  
  - Loading skeleton, empty state, validation error, permission denied

- **Anti-patterns**  
  - No complex animations  
  - No more than one accent color  
  - No nested modals

## 6) 建議你下一步怎麼做（不需要我先看網址也能開始）
你可以直接用你正在做的「提示詞管理系統」挑 2 個核心頁：
1) 列表頁（含搜尋/篩選/標籤/操作）  
2) 專案詳情頁（含進度紀錄、附件、按鈕說明）

然後你只要準備：
- 參考站 1 個 + 截圖 2–4 張（或不截圖但用「取用範圍」限制）
- 你希望的主色（例如偏藍/偏紫/偏綠）與「禁用項」

我就可以把它整理成一份你可直接丟給 Coding Agent 的 `ui-guidelines.md`（含 tokens 與元件規格），讓後續產 UI 都能一致、可控、可驗收。
