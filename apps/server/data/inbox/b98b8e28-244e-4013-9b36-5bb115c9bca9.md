## 作法 1（建議）｜用 Vite 建一個可預覽的 React 專案

### 1) 建立專案
```bash
npm create vite@latest my-prompt-manager -- --template react
cd my-prompt-manager
npm install
```

### 2) 把你的 `app.jsx` 放進專案
- 將你上傳的 `app.jsx` 內容複製
- 覆蓋到：`my-prompt-manager/src/App.jsx`（或 App.jsx 內容整段替換）

> Vite 預設在 `src/main.jsx` 會 `import App from './App.jsx'`，所以你放到 `src/App.jsx` 最省事。

### 3)（若你要用 Tailwind）安裝與設定
```bash
npm install lucide-react tailwindcss postcss autoprefixer
npx tailwindcss init -p
```

**tailwind.config.js**（確認 content 有掃到 src）
```js
export default {
  content: ["./index.html", "./src/**/*.{js,jsx,ts,tsx}"],
  theme: { extend: {} },
  plugins: [],
}
```

**src/index.css**（加入 Tailwind 指令）
```css
@tailwind base;
@tailwind components;
@tailwind utilities;
```

### 4) 啟動預覽
```bash
npm run dev
```

終端機會顯示類似：
- `Local: http://localhost:5173/`

用瀏覽器開該網址即可看到畫面。

## 方案 B｜本機仍要跑，但「硬碟占用更省」：用 pnpm 取代 npm
`node_modules` 大的根本原因是：每個專案都各自存一份依賴的副本。

pnpm 的設計是把依賴存到**全域 content-addressable store**，專案內用 hard link / symlink 引用，可顯著降低多專案重複占用。citeturn0search21turn0search9

**做法（Windows PowerShell）**
```powershell
npm i -g pnpm
pnpm install
pnpm dev
```

適用情境：你會做很多 prototype / 多個前端專案，想讓硬碟不要每個專案都膨脹。

---

## 方案 C｜你只想留「可預覽的成品」而不是整包開發環境：只保留 dist
Vite 打包後會產出可部署的靜態檔，預覽也可以直接用 `npm run preview` 來看 `dist`。citeturn0search8turn0search4

**步驟**
```bash

```

- **保留 `dist/`**
- **刪掉 `node_modules/`**（需要再開發時再 `npm install` 回來）

這樣「專案資料夾」就會非常小，適合交付或備份（但注意：要再開發就必須重新安裝依賴）。

## AI

理解，你的目的不是「把網頁跑起來」而已，而是 **用 SpecKit 開發時，前端實作必須長得跟你這份雛形/設計一致**。在這個目標下，「輕量」的關鍵不在於完全不要 `node_modules`，而是：

- 把「設計」變成 SpecKit 的**不可違反契約（UI Contract）**
- 把「實作驗收」變成每次產出都要過的**一致性檢核（手動或自動）**
- 讓開發環境的成本可控（例如用 pnpm、或把 preview 與 build/dep 分離）

下面是我建議的落地做法（可直接套到你所有 SpecKit 專案）。

---

## 1) 建立「唯一真實來源」：Prototype + UI/UX Spec 固定放在 repo

在你 Speckit 專案根目錄新增（或確認已有）：

```
/ui/
  ui_prototype.tsx          # 你的單檔雛形（App.jsx / tsx）
  uiux_spec.md              # UI/UX 規格（版面、元件、狀態、CTA階層）
  ui_checklist.md           # 驗收清單（逐條勾選）
```

原則：**工程師（含 Coding Agent）不得憑空「設計」，只能「實作」**，新增 UI 只能先改 `uiux_spec.md` 再做程式。

---

## 2) 把 UI 契約寫進 SpecKit 的 constitution（這一步最關鍵）

在 `.specify/constitution.md` 或你 SpecKit 的規範文件中加入一段「UI Contract」條款，讓 Agent 每次都必須遵守：

**UI Contract（建議內容）**
- 以 `/ui/ui_prototype.tsx` 與 `/ui/uiux_spec.md` 為準；未列規格不得自行新增視覺語言。
- 版面結構、CTA 層級、表格/看板呈現邏輯必須一致；差異需先回到 spec 變更。
- Tailwind class / spacing / typography 採既定 token（若尚未建立 token，先建立再重構）。
- 每次提交需附：對照清單（哪些頁面對齊、哪些差異、差異理由與補救）。

這樣 SpecKit 產出（plan/tasks/implementation）才會「被規格鎖住」。

---

## 3) 把你的雛形「拆成可重用元件」，但外觀不變

你的雛形通常是單檔 App。實作時請採「先凍結外觀，再抽元件」策略：

**順序**
1. 先把雛形完整搬到 `src/App.jsx`，確保畫面一致。
2. 再把 UI 逐段抽成元件（例如 `ProjectTable`, `PromptBoard`, `EditorHeader`, `DangerZone`）
3. 抽元件時不得改 class / spacing，除非 spec 有寫。

這樣你可以避免「一拆元件就走樣」，也最符合你要的「實作結果跟雛形一樣」。

---

## 4) 規劃一個「最小可行的 UI 對齊驗收」流程（不一定要重工具）

你可以分兩階段：

### 4.1 雛形期（最低成本）
- 用 `/ui/ui_checklist.md` 做逐條勾選（CTA、間距、版面、表格線、看板欄位…）
- 每次 Speckit 產出後，要求 Agent 在 PR/Commit 訊息附上「清單對照結果」

### 4.2 穩定後（建議加，但可選）
- 用 Playwright 做**視覺快照**（screenshot regression）
  - 這會增加一些依賴，但能把「長得一樣」變成可自動判斷
  - 好處是你不需要每次人工逐頁比對

如果你現階段最在乎「輕量」，先做 4.1 就夠，等 UI 穩定再上 4.2。

---

## 5) 關於你在意的 129MB：用「長期輕量」而非「一次性不裝」

你現在看到的 129MB，主要是 `node_modules`。要兼顧「本機可開發」與「占用可控」，我建議：

### 5.1 改用 pnpm（對你這種多專案 prototype 很有效）
- 你的每個專案不會都各自存一份依賴，硬碟總量會下降很多（尤其你開多個 prototype 時）。

### 5.2 專案交付/備份只保留 dist（開發時再裝回來）
- 你要的是「依照設計開發」，開發期難免需要依賴；但你可以把交付物維持很小。

---

## 6) 給你一段「每次丟給 Coding Agent 的固定指令」（可直接複用）

你之後每個 Speckit 任務都用這段開頭（貼在你的 Prompt 模板裡）：

> 你要實作前端時，必須以 `/ui/ui_prototype.tsx` 與 `/ui/uiux_spec.md` 為唯一標準。  
> 禁止自行發明新的視覺語言（色彩、間距、按鈕樣式、表格線、卡片陰影、字級階層）。  
> 實作每個頁面後，請逐條對照 `/ui/ui_checklist.md` 回報：符合/不符合/差異原因/修正方案。  
> 若需要改 UI，先改 spec，再改程式；不得直接改程式造成規格漂移。

這一段會明顯降低你說的「做到最後才發現跟想的差太多」。
