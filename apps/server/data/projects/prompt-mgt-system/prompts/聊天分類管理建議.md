## AI

以下提供一套「可落地、可擴充」的聊天分類架構，目標是讓你後續在管理（搜尋、回溯、交接、重用內容）時一致且高效率。你可以同時採用 **主分類（單選）** + **標籤（多選）** 的方式，避免分類越分越細、最後失控。

## 一、建議主分類（8–10 類，單選）

> 原則：主分類用來回答「這串聊天主要在處理什麼工作型任務？」

1. **售前/提案與客戶溝通（Presales & Proposal）**  
   - 用途：需求探索、可行性、初估工期/報價、對客戶說法、簡報重點  
   - 例：企業資金詢價平台、玉山資訊簡報、方案比較、競業避嫌說明

2. **需求規格與系統設計（Requirements & Design）**  
   - 用途：需求彙整、流程圖、資料規格、模組設計、RFP/SDD  
   - 例：需求彙整與功能規格、Mermaid 流程圖修正、魚骨圖模組拆解

3. **實作/開發與部署（Build & Deploy）**  
   - 用途：批次檔、部署問題、環境設定、程式框架、專案結構  
   - 例：正式環境啟動伺服器的 bat 修正、工具鏈整合（VS Code/Codex）

4. **自動化與工作流（Automation & Workflow）**  
   - 用途：n8n、Power Automate（雲端/桌面）、RPA、流程節點設計  
   - 例：Power Automate Desktop vs Cloud 可行性、檔案查找流程、n8n JSON 匯入

5. **測試與品質（Testing & QA）**  
   - 用途：Playwright、自動化測試策略、測試報告、回寫 Excel、錄影截圖  
   - 例：Playwright 安裝/批次測試、腳本生成 Agent、測試流程文件化

6. **資安/治理與風險（Security & Governance）**  
   - 用途：弱掃、合規、Shadow IT 風險、權限、稽核、資料保護  
   - 例：Shadow IT 定義與風險、銀行環境限制、工具治理說法

7. **UI/UX 與產品體驗（UX/UI & Product）**  
   - 用途：介面調整建議、流程順暢度、資訊架構、操作情境  
   - 例：Prompt Management Workspace UI/UX、銀行端回覆管理介面 mockup

8. **內容產製與教材（Content & Enablement）**  
   - 用途：講稿、逐字稿、教學手冊、簡報頁面整理、課程大綱  
   - 例：安裝手冊（含 Q&A）、簡報逐字稿、GAMMA 範本、課程行銷內容

9. **知識管理與提示詞系統（KM & Prompt Ops）**  
   - 用途：提示詞管理、版本控管策略、專案/共用檔治理、工作區規劃  
   - 例：Prompt Management Workspace 規劃、VS Code + Codex 操作情境、共用提示詞治理

10. **研究與選型（Research & Selection）**  
   - 用途：工具比較、平台特性、費用/授權、替代方案評估  
   - 例：平台工具特色與價格、是否有開源替代、兩台機器差異比較

## 二、建議標籤（多選，強烈建議 10–15 個固定集合）

> 原則：標籤用來回答「這串聊天的輸出物/方法/狀態是什麼？」

### 1) 產出物（Deliverable）
- `#Markdown` `#PDF` `#PPT` `#講稿` `#流程圖` `#RFP/SDD` `#SOP/手冊` `#Prompt`

### 2) 技術/平台（Tech Stack）
- `#PowerAutomateCloud` `#PowerAutomateDesktop` `#n8n` `#Playwright` `#VSCode` `#Codex` `#Copilot` `#Docker` `#RAG` `#MCP`

### 3) 情境/對象（Audience）
- `#對客戶` `#對主管` `#內部交接` `#教育訓練` `#銀行場域`

### 4) 狀態（Status）
- `#待確認` `#已確認` `#進行中` `#已完成` `#需重構` `#風險點`

> 管理上的關鍵：**標籤集合要固定，不要無限制擴張**。若要新增標籤，先檢查是否真的無法被既有標籤涵蓋。

## 五、最小可行的管理流程（你可以直接照做）

1. **每串聊天建立時先選主分類（單選）**  
2. **結束時補 3–6 個標籤（多選）**  
3. **固定輸出「可重用資產」到你的知識庫**（例如：md、流程圖、提示詞、SOP）

## 一、整體結構建議（Project → Work Item → Asset）

1. **Project（專案）**：主體，定義目標、範圍、利害關係人、時程、風險與決策。  
2. **Work Item（工作項/議題）**：專案內的任務切分（需求議題、技術議題、交付物、會議、缺陷）。  
3. **Asset（資產）**：可重用輸出（簡報、SOP、流程圖、提示詞、程式碼片段、POC 結果、報價假設）。

你的聊天（Conversation）可視為：  
- 一種 Work Item 的討論紀錄；或  
- 一個 Asset 的生成過程；或  
- 一次 Decision / Issue 的形成歷程。

## 四、聊天層級：加入「專案」後的分類方式（你要的關鍵）

當聊天要能被專案管理使用，聊天除了你原本的 **主分類 + 標籤** 外，建議新增 3 個欄位：

1. **Project Key（必填）**：此聊天歸屬的專案代碼  
   - 例：`PRJ-ESUN-FundingInquiry`、`PRJ-HR-TrainingAutomation`、`PRJ-Internal-PromptOps`

2. **Work Item Type（單選）**：這串聊天在專案裡扮演什麼「工作項」  
   - `#需求澄清` `#設計討論` `#實作排障` `#會議記錄` `#決策紀錄` `#交付物產製` `#風險議題` `#問題單/缺陷`

3. **Asset Link（可選）**：這串聊天產出了什麼資產（或連到資產）  
   - `#產出PPT` `#產出SOP` `#產出流程圖` `#產出提示詞` `#產出程式碼` `#產出報價假設`

這樣你會得到非常穩定的管理能力：  
- 以專案找聊天（Project Key）  
- 以任務類型濾掉雜訊（Work Item Type）  
- 以資產快速再利用（Asset）

## 1) 資料域模型（Domain Model）

### 1.1 Entity
- **Project**：專案主體（目標、範圍、狀態、利害關係人、風險、里程碑）
- **Conversation**：聊天紀錄（歸屬專案、主分類、Work Item 類型、標籤、產出物連結）
- **WorkItem**：工作項（需求/任務/缺陷/議題/會議/決策等，可指派、追蹤狀態）
- **Asset**：可重用資產（SOP/PPT/流程圖/提示詞/程式碼片段/報價假設等）
- **Decision（ADR-lite）**：決策紀錄（背景、方案、結論、日期、影響）

### 1.2 關聯
- Project 1—N WorkItems
- Project 1—N Conversations
- Project 1—N Assets
- WorkItem 可連結 N Conversations / N Assets
- Decision 屬於 Project，可選擇連到 WorkItem

## 3) Key / ID 規則（Codex 必須實作驗證）

### 3.1 Project Key
- 格式：`PRJ-{ORG}-{DOMAIN}-{NAME}-{YYYY}`  
- 例：`PRJ-ESUN-BANKING-FundingInquiry-2025`
- 驗證：只允許 `[A-Z0-9-]`（NAME 可允許大小寫混合，但建議轉成安全字元）
- 需唯一。

### 3.2 Conversation ID / WorkItem ID / Asset ID / Decision ID
- 格式：`{TYPE}-{YYYYMMDD}-{shortId}`  
- TYPE：`CONV` / `WI` / `AST` / `DEC`
- shortId：8 碼（隨機或 hash）

## 7) UI 功能規格（Codex 直接做畫面與路由）

### 7.1 全域導覽
- 左側：Projects / Work Items / Conversations / Assets / Decisions / Search / Settings（Taxonomy 檢視）
- 右側：快速新增（Project / WorkItem / Conversation / Asset / Decision）

### 7.2 Projects
- Projects List：filter（status/type/industry/tags/keyword），排序（updatedAt desc）
- Project Detail：
  - Overview（project.md 渲染 + metadata）
  - Work Items（表格：status/priority/title/due/assignee）
  - Conversations（列表：date/category/title/tags）
  - Assets（列表：assetType/title/status）
  - Decisions（列表：date/title/status）

### 7.3 Conversations
- 支援：建立/編輯 metadata、正文 Markdown 編輯
- 支援：連結 WorkItem / Asset（多選）
- 支援：一鍵轉 Asset（把摘要/內容複製到新 Asset）

### 7.4 Work Items
- Kanban（TODO / IN_PROGRESS / WAITING / BLOCKED / DONE）
- WorkItem 詳情頁：描述、驗收條件、關聯聊天/資產、狀態變更歷史（至少紀錄 updatedAt）

### 7.5 Assets
- Assets List：依 assetType / audience / deliverableTags 過濾
- Asset Detail：內容 + fileRefs（附件路徑顯示）

### 7.6 Search
- 支援跨專案：keyword + tags + entity type
- 顯示結果：依 entity 類型分群

## 9) 驗收條件（Definition of Done）

1. 可建立 Project，並在 `data/projects/{projectKey}/project.md` 生成檔案。  
2. 可在 Project 下建立 WorkItem/Conversation/Asset/Decision，各自產生對應 md。  
3. 可在 UI 以 status/type/tags/keyword 進行過濾與搜尋，且結果正確。  
4. 可連結 WorkItem ↔ Conversation ↔ Asset（雙向在索引可追溯）。  
5. 執行 rebuildIndex 後，`data/index.json` 內容完整、可用於搜尋。  
6. 所有枚舉欄位只能選 taxonomy.json 中的值；非法值需 UI 阻擋。  
7. Project Key / ID 驗證生效，不合規不可建立。

## AI

CTA 是 **Call To Action** 的縮寫，中文常翻作 **「行動呼籲」** 或 **「主要行動按鈕」**。

在 UI/UX 實務上，CTA 指的是「你希望使用者在這個畫面最先、最明確去做的那個動作」，通常會用 **最醒目** 的樣式呈現（例如主色按鈕），以引導使用者完成關鍵流程。

## 在你這份清單裡，CTA 的意思
- **主 CTA（Primary CTA）**：每頁最重要的主要動作  
  - 例：**新增、儲存、上傳、送出、完成**
  - 你規範為：一律 `btn-primary`
- **次要操作（Secondary actions）**：輔助或不影響主要流程的動作  
  - 例：**返回、取消、收合、關閉**
  - 你規範為：一律 `btn-ghost`
- **危險操作（Destructive actions）**：可能造成不可逆或重大影響的動作  
  - 例：**刪除、永久移除、清空**
  - 你規範為：一律 `btn-danger`，且只在編輯狀態或危險區顯示，並用中央 modal 二次確認

## 你寫的「CTA 層級」規則在管什麼
- 「每頁 header 右側只保留一個主 CTA」  
  → 避免同時出現多個「看起來都很重要」的按鈕，讓使用者猶豫。
- 「刪除只在危險區塊/編輯狀態顯示」  
  → 避免誤觸，也符合使用者心理預期（刪除是少數情境）。
- 「二次確認一律使用中央 modal」  
  → 統一互動模式，降低學習成本，也提高風險操作的辨識度。
